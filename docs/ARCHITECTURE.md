# AssetIQ — Team Architecture & Engineering Contract

## 1. Project identity

AssetIQ is an AI-powered equipment memory agent.

AssetIQ remembers the maintenance history of physical equipment and gives technicians an instant, context-aware brief before they work on an asset.

The product loop is:

Technician
→ Service Report
→ MySQL + Hindsight
→ Future Asset Visit
→ Retrieve relevant memory
→ Groq
→ Maintenance Brief
→ New Service Report
→ More memory

The core mission is not to produce a polished dashboard first. The first priority is to make the end-to-end memory loop work for real maintenance history and future briefs.

## 4. System responsibilities

### 4.1 MySQL

MySQL is the structured application truth.

It stores:
- Assets
- Maintenance reports
- Timestamps
- Deterministic application data

MySQL contains the official persisted application facts. It is not the AI memory layer.

### 4.2 Hindsight

Hindsight is the persistent AI memory layer.

It stores:
- Historical context
- Recurring problems
- Technician observations
- Previous repair attempts
- Useful patterns across visits

This is not decorative. Historical information must genuinely be retained and recalled through Hindsight and used to influence the future maintenance brief.

### 4.3 Groq

Groq is responsible for understanding technician input, structuring information where useful, synthesizing historical context, and generating technician-facing maintenance briefs.

Groq is not a replacement for Hindsight. It is a language layer that consumes retrieved memory and produces a useful summary or brief.

### 4.4 Express

Express is the API layer and orchestration layer.

It handles:
- API
- Validation
- Orchestration
- MySQL integration
- Groq service integration
- Hindsight service integration

### 4.5 React

React is the technician-facing UI.

It handles:
- Asset selection
- Maintenance brief
- Service report form
- API integration

React must not directly call Groq or Hindsight.

## 5. Critical architecture rule

React must not directly call Groq or Hindsight.

The required flow is:

React
↓
Express API
↓
Service layer
├── MySQL
├── Groq
└── Hindsight

Groq and Hindsight must be isolated behind service abstractions.

Do not scatter raw SDK calls throughout the backend.

## 6. Canonical maintenance report

Every part of the application must use the following conceptual fields for a maintenance report:

{
  "assetId": "...",
  "symptom": "...",
  "diagnosis": "...",
  "action": "...",
  "partsUsed": "...",
  "outcome": "...",
  "technicianNotes": "..."
}

These names are the canonical contract.

Do not create competing names such as:
- problem
- issue
- repairAction
- notesText

If existing code uses different names, create an explicit mapping instead of silently changing the contract.

Every persisted maintenance event must have a timestamp.

## 7. Asset identity rules

The canonical asset identity is the asset identifier used in the system, and the demo asset is:

HVAC-204

The system must support repeated maintenance interactions for the same asset and must retrieve its historical context from Hindsight, not from a hardcoded AI answer.

## 8. Canonical API contract

### POST /api/reports

The API must:
- validate report
- persist structured report in MySQL
- retain useful memory in Hindsight
- return result

This is the primary maintenance report submission flow.

### GET /api/assets/

The API must return structured asset information.

### GET /api/assets/:assetId/brief

The API must:
- retrieve relevant Hindsight memory
- prepare context
- call Groq
- generate maintenance brief
- return brief

The brief generation flow must use Hindsight recall and Groq synthesis. It must not be a hardcoded response and must not come from a direct MySQL fetch pretending to be memory.

## 9. Maintenance brief contract

The maintenance brief is a technician-facing summary generated from encrypted or attached historical context and current asset context.

It must reflect historical facts retained in Hindsight for the asset and related tasks, and it must be generated by Groq using the retrieved relevant memory as input.

A maintenance brief should not be a mock or a hardcoded string. It must be a result of memory retrieval plus AI synthesis.

## 10. MVP milestone

The system must be able to:

1. Submit a maintenance report for HVAC-204.
2. Store the structured report in MySQL.
3. Retain useful information from that interaction in Hindsight.
4. Submit additional maintenance interactions.
5. Select HVAC-204 later.
6. Request a maintenance brief.
7. Retrieve relevant historical context from Hindsight.
8. Give that context to Groq.
9. Generate a brief containing information from previous interactions.

HINDSIGHT IS NOT DECORATIVE.

Do not simulate Hindsight by simply fetching MySQL rows and sending them to Groq.

The final demo must demonstrate that historical information was actually retained and retrieved through Hindsight and subsequently influenced the AI brief.

Do not hardcode the final maintenance brief.

## 16. Definition of working

The system is working when:
- a maintenance report is submitted
- the structured report persists to MySQL
- Hindsight retains the useful memory
- a subsequent report for the same asset can retrieve relevant memory
- Groq receives that retrieved memory and produces a brief that includes historical context
- the technician-facing flow is usable and demonstrable

## 17. Shared contract boundaries

### 17.1 Frontend contract

The frontend is responsible for:
- rendering the technician workflow
- collecting report data
- sending requests to the API
- displaying asset info and maintenance brief output
- handling loading and errors

The frontend does not decide AI logic or memory logic.

### 17.2 Backend contract

The backend is responsible for:
- validating input
- persisting data
- orchestrating Hindsight interactions
- orchestrating Groq interactions
- exposing API routes
- returning structured JSON results

### 17.3 Groq service contract

The Groq service is responsible for:
- receiving structured context
- producing a maintenance brief or normalized summary
- operating behind a service interface
- receiving prompt inputs from backend orchestration

The Groq service must not be called directly from React.

### 17.4 Hindsight service contract

The Hindsight service is responsible for:
- retaining memory from maintenance events
- recalling relevant historical context for an asset
- preparing memory context for later AI use
- operating behind a backend service interface
- preserving actual historical knowledge across visits

The Hindsight service must not be bypassed with a MySQL fetch masquerading as memory.

## 18. Memory rules

- Hindsight memory is persistent and historical.
- MySQL is deterministic structured application state.
- Memory is not just raw rows from MySQL.
- Historical context must be retained and recalled through Hindsight.
- If no relevant Hindsight memory exists, return that honestly.
- Groq output should reflect historical context when it exists.

## 19. Database vs memory distinction

MySQL stores the application-of-record data.

Hindsight stores the AI memory layer.

The application must keep these distinct.

## 24. Summary of the operating contract

This project is built around a clear separation:

- MySQL = structured truth
- Hindsight = persistent memory
- Groq = generation and synthesis
- Express = orchestration and API
- React = technician interface

The system must not blur these responsibilities.

The canonical report contract, the maintenance loop, and the memory-driven brief generation are the foundation of the implementation.

No later work should redesign these contracts without explicit team agreement and updated architecture documentation.
